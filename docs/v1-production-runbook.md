# V1 Production Runbook

This runbook is the release gate for Startup Radar V1. Production is not currently provisioned: the
`startup-validation` Fly organization contains only staging web/worker and staging PostgreSQL apps.
Do not promote the `production` Git branch until the production Fly app, database, backup, secrets,
and Vercel proxy destination have been created and verified.

## Intended Topology

Browser -> Vercel stable production origin -> same-origin `/api` functions -> Fly web -> PostgreSQL.
The Fly worker has no public route and runs scheduled Radar and offering jobs against the same
database. The browser never receives `DATABASE_URL`, `RADAR_RUN_TOKEN`, provider keys, or the admin
password hash. Groq is the V1 provider; Router stays unset unless separately approved.

Use PostgreSQL 16 or 17 for the first production database. Staging currently runs PostgreSQL 18.1;
Flyway 11.7.2 completes the migrations there but emits a tested-version warning. Choosing 16/17
avoids relying on that warning path without a dependency upgrade during the release freeze.

## Environment Inventory

### Required Secrets - Fly

- `DATABASE_URL`: attached database connection. Never print it. For a pooled managed connection,
  use a direct migration URL for Flyway release commands; the current single URL is suitable for an
  unmanaged Fly Postgres attachment.
- `RADAR_ADMIN_PASSWORD_HASH`: PBKDF2-SHA256 hash generated by `RadarPasswordHashTool`; never store
  the plaintext password in Git or Fly notes.
- `RADAR_RUN_TOKEN`: random server-to-server worker token, at least 64 characters.
- `GROQ_API_KEY`: required because V1 launches with Groq enabled.
- `PRODUCT_HUNT_TOKEN`: server-side Product Hunt API token.

### Required Non-Secrets - Fly

- `RADAR_BROWSER_ORIGIN=https://startup-validation-bot.vercel.app`
- `APP_ALLOWED_ORIGINS=https://startup-validation-bot.vercel.app`
- `RADAR_APP_URL=https://startup-validation-bot.vercel.app/#/radar`
- `RADAR_AUTH_SECURE_COOKIE=true`
- `RADAR_AUTH_SAME_SITE=Strict`
- `RADAR_ENABLE_AI=true`
- `RADAR_AI_PROVIDER=groq`
- `RADAR_AI_MODEL=openai/gpt-oss-20b`
- `RADAR_DEEP_DIVE_MODEL=openai/gpt-oss-120b`
- `RADAR_AI_MAX_ITEMS_PER_RUN=25` (use a smaller value for the first controlled run if desired)
- `RADAR_AI_MAX_RETRIES=2`
- `RADAR_ENABLE_HACKER_NEWS=true`
- `RADAR_DEMO_FIXTURE_ENABLED=false`
- `SEC_EDGAR_USER_AGENT`: descriptive application name plus a monitored contact address.
- `OFFERING_DISCOVERY_CRON=0 15 7 * * *`
- `RADAR_TIME_ZONE=America/New_York`
- `RADAR_DISCOVERY_CRON=0 0 6 * * *`
- `RADAR_WATCHLIST_CRON=0 30 6 * * *`
- `RADAR_TRENDS_CRON=0 0 7 * * SUN`
- `RADAR_DIGEST_CRON=0 0 8 * * MON`

### Required Non-Secret - Vercel

- `RADAR_BACKEND_ORIGIN=https://<production-fly-app>.fly.dev`, server-side only.

Do not set `VITE_RADAR_API_BASE_URL` in Vercel. The production SPA must use the same-origin proxy.
Do not put any Fly secret or provider credential in a `VITE_*` variable.

### Optional

- `RADAR_RSS_URLS`: leave unset initially, then enable the existing TechCrunch venture preset from
  authenticated Admin after the base launch is healthy.
- `ROUTER_API_KEY`, `ROUTER_BASE_URL`, `RADAR_ROUTER_ROUTINE_MODEL`,
  `RADAR_ROUTER_DEEP_DIVE_MODEL`: keep unset for initial V1.
- `RADAR_EMAIL_SEND_URL`, `RADAR_EMAIL_TOKEN`, `DEAL_SCOUT_RUN_URL`,
  `DEAL_SCOUT_RUN_TOKEN`: only when the corresponding server-side service is deliberately enabled.
- Authentication durations, throttle limits, discovery limits, lease duration, SEC bounded-crawl
  limits, and AI prompt/schema versions already have production-safe defaults in
  `application.properties`.

### Disabled For Initial V1

- `RADAR_DEMO_FIXTURE_ENABLED` must remain `false`.
- Router variables remain unset and `RADAR_AI_PROVIDER` remains `groq`.
- `VITE_RADAR_API_BASE_URL` remains unset in Vercel.
- Unused Deal Scout/email integration URLs remain unset.

Before deployment, compare secret names with `fly secrets list --app <production-app>` and Vercel's
production environment screen. Compare names only; never paste values into a ticket or terminal log.

## Pre-Deploy Gate

1. Record `git rev-parse origin/production`, the stable Vercel production deployment ID, and any
   existing Fly production release ID. On the first deployment, explicitly record that no Fly release
   exists.
2. Create a dedicated production Fly app and a dedicated PostgreSQL 16/17 database in the Startup
   Validation organization. Do not reuse staging or any trading-bot resource.
3. Provision reasonable backup capability. For unmanaged Fly Postgres, create with
   `fly postgres create --enable-backups` or run `fly postgres backup enable -a <db-app>` before
   attaching it. Managed Postgres is also acceptable and includes managed backups.
4. Verify a backup exists with `fly postgres backup list -a <db-app>`. Record the latest backup ID and
   timestamp. A provisioned database with no successful backup is a release blocker.
5. Verify the restore path without touching production: WAL backup restore must create a separate
   destination cluster (`fly postgres backup restore <restore-test-app> -a <db-app>`). Validate the
   restored database, then remove only that disposable restore-test app after explicit confirmation.
6. Attach the database to the production app and verify `DATABASE_URL` is present by name only.
7. Set every required environment variable above. Confirm the Vercel origin values contain no path,
   trailing slash, wildcard, preview hostname, or hash route.
8. Record CI for the exact main SHA: Maven verify including all Testcontainers tests; frontend test,
   lint, build, and production audit; Fly strict config validation; `git diff --check`.
9. Confirm `production` still contains only its history-only initialization commit ahead of the old
   common ancestor. Promote with a normal merge of `main` into `production`; never reset or force push.

## Deploy

These are the commands for the separately approved deployment task, not this readiness audit.

1. Merge `main` into `production` normally and push `production`.
2. Deploy Fly from the exact production SHA. The release command runs Flyway V1-V11 with Hibernate
   DDL disabled before the web/worker replacement.
3. Require a successful release command and confirm the Flyway schema history is at V11. Do not run
   `flyway clean` and do not manually edit schema history.
4. Confirm one 1 GB `web` Machine and one 512 MB `worker` Machine. Only web is publicly routed; one web
   Machine stays warm. Confirm readiness includes database health.
5. Let the Vercel Git integration deploy the `production` branch. Confirm the stable production URL,
   not a preview URL, uses `RADAR_BACKEND_ORIGIN` for the new Fly app.
6. Do not manually trigger broad discovery until the browser and persistence checks pass.

## Post-Deploy Smoke

1. `GET /api/radar/health` through Vercel returns 200.
2. Signed-out protected Radar and Deal Workspace requests return 401.
3. Valid login succeeds; the cookie is HttpOnly, Secure, SameSite=Strict, scoped to `/api`, and no
   session credential appears in localStorage.
4. Radar Home, Companies, company profile, Watchlist, Trends, Offerings, Deal Scout, Deals, Deal
   Workspace, and Admin load through Vercel without direct browser-to-Fly requests.
5. Create one clearly named disposable deal workspace, save Review Tracking, reload, and verify all
   server-backed fields persisted. Delete only that disposable record.
6. Verify Admin status: database healthy, configured provider/model names, source status, job status,
   AI counters, and offering diagnostics contain no secret values.
7. Run a digest preview, not a send. Run one limited discovery job, then one offering-discovery job.
   Verify lease completion, bounded source errors, idempotent rerun, and no duplicate company/offering.
8. Verify Fly logs for web startup, worker startup, migration completion, provider failures, source
   failures, and graceful job completion. The old GitHub Deal Scout digest workflow remains manual.
9. Log out and confirm protected API requests return 401 and private UI state is cleared.

## Rollback

Prefer application rollback while keeping the forward-compatible V1-V11 schema.

- Git: revert the release merge on `production` or normally merge a tested corrective commit. Do not
  rewrite branch history.
- Fly: deploy the recorded previous image/release or exact previous Git SHA, then verify readiness and
  logs. A pre-Radar application may not understand every new table, but additive unused tables are
  harmless; validate the target binary against V11 before rollback.
- Vercel: use the recorded deployment to roll back/promote the previous stable frontend deployment,
  keeping its matching environment configuration.
- Database: do not casually migrate backward. V1-V11 are additive except the narrow V8 data cleanup,
  and application rollback should normally leave the schema at V11. Restore into a new database only
  for confirmed data corruption or an incompatible migration, validate it separately, and then
  deliberately reattach the app. Never restore over the only production copy.

## Dry-Run Sequence And Manual Actions

The intended production task is: verify CI -> create production app/database -> enable and verify a
restorable backup -> set Fly secret names and exact origins -> set Vercel `RADAR_BACKEND_ORIGIN` ->
normal main-to-production merge -> Fly deploy/release migration -> backend health -> Vercel stable
deployment -> browser auth/persistence smoke -> worker health -> one limited manual job.

Manual user actions are limited to supplying the admin password hash and API secret values from the
password manager, confirming the Vercel production environment and branch settings, and explicitly
approving the actual production merge/deployment. No production write occurs during readiness review.
